# Casos de Teste — Integração Pedidos ↔ Catálogo

Verifica a colaboração **real** entre `order-service` e `catalog-service`. Os testes de integração do próprio SUT (`OrderApiIT`) usam um catálogo simulado (MockWebServer). Aqui os dois serviços rodam de verdade, e a falha é injetada só quando o cenário exige.

**Injeção de falhas (nível API+FI):** o ambiente de teste usa um *override* do Docker Compose que aponta `CATALOG_BASE_URL` do `order-service` para um proxy (WireMock em modo proxy diante do catálogo real). O proxy permite contar chamadas, inspecionar headers, injetar latência e erros. É **apenas configuração por variável de ambiente**, já suportada pelo SUT (`sut/README.md`), sem alteração de código. Cada caso restaura o estado no teardown. Dois modos de indisponibilidade são distinguidos, porque o SUT os trata por caminhos diferentes:

- **Conexão interrompida** depois de estabelecida: o proxy derruba a conexão (*fault* `CONNECTION_RESET_BY_PEER`). Simula um catálogo que cai no meio da chamada.
- **Destino inacessível** (conexão recusada ou nome não resolvido): o container do proxy é parado durante o caso.

**Mudanças de dados no catálogo (nível API+DB):** feitas diretamente no MongoDB, porque não há endpoint de escrita (RN-21). São sempre revertidas no teardown, e essas classes executam em série.
